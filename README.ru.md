# xcui-data

Данные, которые читает [Xray Config UI Editor](https://github.com/bropines/xray-config-ui-editor), в виде обычных JSON-файлов: какое клиентское приложение какой User-Agent отправляет, какие форматы умеет импортировать, как страница подписки его открывает, где его скачать и какой у него логотип.

[English](README.md)

## Как данные попадают в редактор

- **Каждое изменение в `main`**, прошедшее проверки, публикуется в <https://bropines.github.io/xcui-data/data.json>. Редактор скачивает этот файл при запуске. Исправление здесь доходит до всех копий редактора без релиза чего-либо.
- **Каждый тег версии** (`v0.2.0`) прикладывает tarball пакета к GitHub Release. Редактор ставит пакет оттуда и вшивает снимок данных в свою сборку. Этот снимок он показывает, пока не пришла скачанная копия, а также когда до Pages не достучаться.
- Скачанную копию редактор проверяет той же схемой, что и CI. Он берёт её, только если она валидна и не старше снимка, который у него уже есть. Сломанный файл не пройдёт CI, а если бы и прошёл, редактор оставил бы то, что у него было.

## Что здесь лежит

| путь | что |
| --- | --- |
| `clients/apps/<id>.json` | одно приложение: User-Agent, форматы, диплинки, ссылки на скачивание, ключ логотипа, источники |
| `clients/order.json`, `samples.json`, `notation.json`, `i18n/<lang>.json` | порядок приложений, User-Agent из реального трафика, обозначения, переводы текстов |
| `rules/blueprints.json`, `rules/i18n/<lang>.json` | правила Response Rules, которые пишет «Создать из базы» (в порядке панели), и переводы их описаний |
| `geo/sources.json` | откуда страница берёт geoip / geosite (`check` — проверка настоящим ядром, `viewer` — просмотр списков) |
| `subpage/base-texts.json` | базовые тексты страницы подписки |
| `icons/<ключ>.svg` | логотипы приложений, которых нет в стандартной странице Remnawave |

Раз в неделю (`bun run links`) проверяется, что geo-файлы по-прежнему отдаются странице и примерно того размера, что указан, а ссылки на скачивание живы.

## Как править приложение

Каждое приложение — отдельный файл `clients/apps/<id>.json`. Править можно прямо на GitHub (кнопка с карандашом) или локально. В VS Code строка `$schema` в начале файла даёт автодополнение и подсвечивает ошибки прямо при наборе.

У каждого утверждения есть `src` — ключи в разделе `sources` этого же приложения. Каждый источник говорит, где факт прочитан: `{ "ref": "owner/repo@tag:path:lines", "kind": "source" }`. Виды источников (`kind`):

| kind | что значит |
| --- | --- |
| `source` | прочитано в коде приложения на указанном теге |
| `docs`, `release-notes` | так пишет разработчик |
| `remnawave` | код или документация Remnawave |
| `operator` | замерено на рабочей панели (обезличено) |
| `third-party` | чужие замеры или тесты |
| `inferred`, `unverified` | выведено, а не увидено |

Что ещё важно:

- **Регулярки** (`uaPatterns[].regex`, `gates[].regex`) пишутся для правила Response Rules в Remnawave с выключенной чувствительностью к регистру. Панель переводит в нижний регистр и сам шаблон, поэтому пишите их строчными и не используйте `\D \S \W \B`. Каждый шаблон должен совпадать со своим `example`.
- **`downloads`** — ссылки по платформам (`ios`, `macos`, `tvos`, `android`, `androidtv`, `windows`, `linux`, `openwrt`). Только `https` и только те ссылки, которые даёт сам разработчик. Ссылки на магазины не угадываем.
- **`brandIcon`** — ключ в SVG-библиотеке, под которым рисуется логотип. Это ключ из стандартной страницы Remnawave (`Happ`, `Throne`…) или файл `icons/<ключ>.svg`.
- **`deepLinks[].template`** — шаблон ссылки: `{URL}` — ссылка подписки как есть, `{URL_ENC}` — она же через `encodeURIComponent`, `{NAME}` — отображаемое имя, `{B64:…}` — base64 того, что внутри.

### Как добавить приложение

1. Создайте `clients/apps/<id>.json` (удобно скопировать похожее приложение).
2. Добавьте `<id>` в `clients/order.json` на то место, где редактор должен его показывать.
3. Добавьте в `clients/samples.json` User-Agent, который приложение действительно отправляет.
4. Добавьте русские переводы его текстов в `clients/i18n/ru.json`. CI назовёт каждый недостающий.

### Тексты и переводы

Данные пишутся по-английски, а `clients/i18n/ru.json` сопоставляет каждому английскому тексту русский. Тексты-обозначения (`1|true`, `upload=; download=; total=; expire=`) кладутся в `clients/notation.json` и показываются как есть. Если поправить английскую фразу, старый перевод перестанет ей соответствовать, и CI не пройдёт, пока у новой фразы не появится свой перевод.

## Проверки

```bash
bun install
bun run check     # все файлы по схеме и в формате репозитория
bun test          # источники, регулярки, примеры User-Agent, полнота переводов
bun run format    # переписать все JSON в формате репозитория
bun run build     # dist/ (пакет) и schema/client-app.schema.json
```

Проверки выводят все проблемы сразу, у каждой указаны файл и путь внутри него.
